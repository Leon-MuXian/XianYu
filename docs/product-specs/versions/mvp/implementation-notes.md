# 闲遇 MVP Implementation Notes

版本：MVP  
文档日期：2026-05-30

## 1. 目录与原型约定

- MVP 实现依据：`docs/design-docs/versions/mvp/prototype.html`。
- MVP 是当前唯一正式版本，不依赖其他版本文档。
- 工程实现只以当前 MVP 版本包与当前 UI 设计稿为依据。

## 2. 建模原则

- 不用行业词做底层领域模型。底层使用 `ServiceItem`、`Resource`、`StaffAccount`、`BookableSlot`。
- UI 文案可按店长自填服务范围显示“课程/服务/项目/时段”，但数据结构保持通用。
- 服务范围由店长自行填写并按标签数组存储，不提供系统预置行业枚举、推荐标签或模板选择。
- 会员卡是门店线下售卖和系统内发放的权益，不是平台支付商品。
- 报表是经营记录聚合，不是财务结算系统。

## 3.1 租户开通口径

- MVP 不提供平台后台人工新建租户入口。
- 店长首次微信登录且系统未找到已绑定租户时，后端自动创建 `Tenant`，初始状态为 `trialing`，试用期天数从平台配置读取；初始默认值为 30 天。
- 自动开通后，店长进入 O-START 清单式开店流程；门店资料、营业时间和资源仍由店长在店长端完成。
- 平台后台只管理已经自动开通的租户，用于查看状态、冻结账户、延期并解冻、配置客服微信和维护平台运营配置。
- 自动开通事件应写入操作记录，触发来源标记为 `store_owner_first_login` 或等价系统来源。

## 3.2 服务项目选择口径

- 店长端创建服务项目时，适用资源和可履约员工均为下拉多选。
- 停用资源和停用员工在下拉中可展示原因，但不可被选中。
- 排期发布时只能从服务项目已选的资源和员工范围内继续选择具体履约对象。

## 3.3 会员卡模板类型

- MVP 仅提供次数卡和期限卡，不提供组合卡。
- 次数卡保存总次数、有效期、低余额提醒阈值、适用服务和适用员工。
- 期限卡保存有效期、到期提醒、适用服务和适用员工，不展示剩余次数。
- 面向店长的发卡成功页只展示邀请码、绑定状态和门店实收金额；发卡前默认已完成线下收款，不提供欠款或部分实收状态。

## 3.4 门店资料展示

- `Store.name_key` 由门店名称经过 Unicode NFKC、首尾空白清理、连续空白折叠和小写转换生成，并建立全局唯一约束；应用层预检查用于即时反馈，数据库约束负责处理并发竞争。
- `Store.city_code`、`district_code`、`detail_address` 保存结构化地址，`address` 由服务端查询行政区划名称后合成，前端不得提交可信的城市或区/县名称。
- `AdministrativeCity`、`AdministrativeDistrict` 通过 Flyway 基线在首次启动时随数据库初始化，查询接口只返回已启用数据；不得在小程序内维护完整行政区划映射。
- `Store.contact_phone` 保持必填自由文本，只限制数据库字段长度，不做格式或唯一性校验。
- `Store.business_categories` 存储店长自填服务范围，限制 1 到 6 个短标签；API 和开店草稿使用 `serviceScopes` 字段。
- 员工端登录后应可读取归属 `Store` 的名称、地址、联系电话、营业时间和服务范围摘要。
- 会员端绑定邀请码前应展示目标 `Store` 资料供核对，绑定后应在卡包或约课首页展示门店资料摘要；两处摘要都应包含营业时间。
- O-START 三个必填项完成后由顶部完成态和三条已完成清单提供确认，创建门店按钮直接解锁；不再生成重复的完整门店预览或额外确认卡。
- 门店资料展示不引入门店图片、头像、二维码或其他文件上传。

## 3.5 首次开店草稿

- 首次登录且无门店的店长进入 O-START 后，系统为当前 `tenant_id` 和 `owner_openid` 创建或读取 `StoreOnboardingDraft`。
- 新用户权益告示的确认状态按店长身份持久化到服务端；不得使用跨账号共享的设备级缓存决定是否展示。
- `StoreOnboardingDraft.store_profile_draft` 保存门店名称及规范化键、服务范围、城市代码与名称、区/县代码与名称、详细地址、后端合成地址和联系电话；草稿保存不占用门店名称。
- `StoreOnboardingDraft.business_hours_draft` 保存按星期配置的营业/休息和开始结束时间。
- `StoreOnboardingDraft.resources_draft` 保存资源名称、类型、容量、启用状态和排序。
- `completion_status` 至少包含 `store_profile_done`、`business_hours_done`、`resource_done`。其中 `resource_done` 要求至少 1 个启用资源。
- O-STORE、O-HOURS、O-RESOURCE 保存成功后返回 O-START，由 O-START 重新拉取草稿并刷新完成状态。
- 创建门店按钮不依赖前端页面栈判断，只依赖后端返回的完成状态。最终提交时后端再次校验行政区划和门店名称，成功后创建 `Store` 和 `Resource`，删除或标记草稿为 `converted`，并返回 O-DASHBOARD 跳转信息；数据库门店名称唯一约束冲突必须转换为可识别的业务错误。
- O-START 的创建前预览由 `store_profile_draft` 和 `business_hours_draft` 合成，资源草稿只用于判断是否满足创建门店条件，不进入门店资料摘要。

## 4. 状态建议

### 4.1 租户状态

- `trialing`：试用中。
- `expiring`：7 天内到期。
- `frozen`：已冻结。
- `extended`：已人工延长。

### 4.2 员工账号状态

- `active`：启用，可登录，可进入新排期选择。
- `disabled`：停用，禁止登录，不进入新排期选择，历史记录保留。
- 员工登录接口不携带租户或门店标识，因此 `StaffAccount.login_name` 必须全平台唯一。创建、修改和登录统一使用 Unicode NFKC、去除首尾空白和小写转换后的账号；应用层预检查用于字段级即时反馈，数据库全局唯一约束负责并发竞争的最终裁决。
- 创建和修改撞号统一返回 HTTP 409、错误码 `STAFF_LOGIN_NAME_TAKEN`；修改时排除当前员工自身。停用账号继续占用登录账号，物理删除后才释放。
- 店长端复制员工账号入口仅出现在员工列表行，复制员工姓名、登录账号和当前登录密码；修改抽屉打开时按员工读取并回显密码，列表接口只返回凭据是否可用，不批量解密或下发全部员工密码。新增员工抽屉和修改员工抽屉不再放置重复的独立复制卡片。
- 员工登录继续只校验 PBKDF2 哈希。可恢复凭据保存在独立 `staff_credential_secret` 表，使用 AES-256-GCM、随机 nonce、`tenant_id + staff_account_id` AAD 和版本化 keyring 加密；查看接口执行租户归属校验、限频、无密码审计并返回 `no-store`。明文密码不得进入业务表、幂等响应、审计字段或日志；密码重置或员工停用后必须撤销该员工全部已有会话。历史仅哈希账号无法恢复原密码，完成一次密码设置后即可进入直接查看和复制流程。
- 删除账号为物理删除操作，必须先校验是否存在关联服务项目、会员卡适用范围、未来排期等项目；有关联项目时禁止删除并提示用户先解除关联。

### 4.3 会员卡状态

- `active`：可用。
- `low_balance`：低余额预警。
- `expiring`：即将到期。
- `expired`：已过期。
- `empty`：次数已用完。
- `suspended`：店长手动暂停。

### 4.4 预约状态

- `reserved`：已预约。
- `cancelled`：已取消。
- `waitlisted`：候补。
- `arrived`：已到店。
- `deducted`：已核销。
- `note_done`：已记录。

### 4.5 线下实收记录

- 发卡前店长已完成线下收款，发卡保存后记录本次实收金额。
- 可记录 `pay_method_label`，例如现金、微信线下、支付宝线下、其他；该字段只是文本标签。
- 退费、补差价和线下售后处理不进入 MVP 店长端流程。

## 5. 权限

| 角色 | 权限 |
| --- | --- |
| StoreOwner | 门店建档、资源、服务、员工、会员卡、会员、排期、报表、客服 |
| Staff | 登录、完善资料、查看自己服务、到店、核销、文本记录 |
| Member | 绑定、查看卡包、预约、取消、候补、查看记录 |
| PlatformAdmin | 查看租户试用状态、冻结账户、延期并解冻、客服微信 |

## 6. 冻结规则

- 冻结按 Tenant 生效。
- 冻结不删除任何业务数据。
- 店长端业务新增/编辑/发布全部禁用，报表只展示摘要。
- 员工端名单、到店、核销、记录全部禁用。
- 会员端约课、取消、候补禁用，只能查看只读卡包摘要。
- 后台延长期限并解冻后，三端恢复。
- 系统定时冻结试用或延长期限已过期且尚未冻结的租户，并写入系统来源审计记录。

## 7. 会员卡与报表规则

- `CardTemplate.sale_price_yuan` 是默认售价。
- `MemberCard.sale_price_yuan` 是本次发卡实际售价，默认带出模板售价。
- `OfflineSaleRecord.sale_amount_yuan` 用于报表销售额。
- 不生成在线支付订单，不调用支付接口。
- 可记录 `pay_method_label`，例如现金、微信线下、支付宝线下、其他；该字段只是文本标签。
- 销售额统计按已生成的线下售卡记录汇总实收金额。
- 核销统计来自 `DeductionRecord`，不得从会员卡余额倒推。
- 低余额预警优先使用模板阈值，未配置时次数卡默认阈值为 2 次。
- 即将到期默认 14 天内。

## 8. 登录与集成

- 店长和会员微信登录仅获取 openid。
- 不调用微信授权手机号。
- 员工账号密码认证由业务系统提供。
- 平台后台账号由内部创建，不开放注册。
- 客服微信只配置文本微信号和展示文案，不上传二维码。
- 微信订阅消息可作为后续增强；MVP 文档不要求实现。

## 9. 文件上传禁令

以下能力不进入 MVP：

- 头像上传。
- 门店图片上传。
- 员工资质上传。
- 客服二维码上传。
- 附件上传。
- 会员反馈图片上传。

如 UI 需要头像或二维码，占位应由系统生成文字标识或静态样式。

## 10. 埋点

- 店长微信登录、创建门店、保存资源、创建员工、创建服务、创建会员卡、发卡、发布排期、查看报表、点击客服。
- 员工登录、完善资料、查看名单、到店确认、核销确认、提交服务记录。
- 会员登录、绑定邀请码、查看卡包、查看服务、确认预约、取消预约、无可用卡提示、查看记录。
- 后台登录、查看租户列表、冻结账户、延期并解冻、保存客服微信、修改平台配置。

## 11. 风险

- 通用业态会导致文案泛化，建议服务项目页面支持店长自定义服务类型。
- 报表不是财务系统，需在页面明确“线下录入统计”。
- 无文件上传会降低头像和二维码展示丰富度，但能保持 MVP 简洁。
- 不做线上支付会增加人工续费和线下售卡录入成本，但符合当前商业边界。

## 12. UI 实现补充

- 移动端以 390px 宽画板为基准，真实实现不得固定 390px 宽度，必须支持不同微信小程序机型自适应。
- 店长端底部导航固定为：工作台、排期、会员、报表、我的。员工管理可从工作台和我的进入。
- 员工端底部导航固定为：今日、名单、核销、记录、我的。
- 会员端底部导航固定为：首页、预约、卡包、记录、我的。
- 触控区域不小于 44px。
- 表单保留 label、输入态、错误提示、提交反馈。
- 状态使用颜色、文字和短说明三件套。

### 12.1 断点与长内容

- 小程序端必须验证 320px、375px、390px、430px 四个宽度；390px 仅为原型基准，页面根容器、顶部栏、底部导航、抽屉和底部操作必须适配不同机型安全区。
- 小程序页面根节点统一设置 `overscroll-behavior-y: none` 抑制滚动链和边界回弹；O-LOGIN 和 O-START 固定首屏使用页面级 `disableScroll` 禁止无内容时的上下拖动，并通过矮屏断点保证内容完整。列表、表单和报表等内容页保留原生页面滚动，`disableScroll` 不得配置到全局 `app.config`。
- 平台后台必须验证 1024px、1280px、1440px、1920px 和宽表格场景；后台不做手机端卡片流，但必须支持不同桌面和笔记本屏幕大小自适应。
- 小程序端不得出现横向滚动；后台宽表格允许横向滚动或关键列固定。
- 后台窄屏时允许筛选换行或折叠次要筛选，但主搜索、状态筛选和行操作必须保持可访问；超宽屏时内容区不应无限拉宽到难以扫读。
- 门店名、服务名、会员卡名最多展示两行，超过两行截断，并在详情页或展开态展示完整内容。
- 地址、营业时间和服务范围允许换行；服务范围达到 6 项时不应挤压主操作。
- 金额、次数、预约数、核销数等数字列应右对齐或使用等宽数字。

### 12.2 首屏任务约束

核心页面首屏最多保留 1 个主任务和 3 个次任务：

| 页面 | 主任务 | 次任务 |
| --- | --- | --- |
| O-START | 完成三项必填并创建门店 | 门店资料、营业时间、履约资源。 |
| O-DASHBOARD 创建后待办 | 推进开放预约前下一步 | 创建员工、设置服务、创建会员卡。 |
| O-DASHBOARD 运营态 | 今天先处理什么 | 到店/核销、低余额、临期会员。 |
| O-REPORT | 看清销售额、预约、到店、核销 | 售卡明细、预约到店、会员卡提醒。 |
| O-SCHEDULE-HOME | 找到待发布或异常时段 | 日期、复制、预检异常。 |
| O-MEMBER-HOME | 添加会员或处理会员卡预警 | 待绑定、余额不足、即将到期。 |
| A-TENANTS | 搜索租户并处理状态 | 状态筛选、到期筛选、行操作。 |

超过首屏任务上限的信息应进入下方分组、详情页或报表明细，不应继续堆在首屏。

### 12.3 表单反馈状态

保存、发布、创建员工、发卡、确认预约、确认核销、取消预约、冻结租户、延期并解冻和修改平台配置必须覆盖：

- `loading`：按钮进入处理中，重复提交禁用。
- `success`：展示明确成功文案，并返回来源页、刷新列表或进入结果页。
- `field_error`：字段旁展示错误，表单顶部展示错误摘要。
- `form_error`：保留输入，说明失败原因和下一步。
- `partial`：说明已保存项和待处理项。
- `disabled`：说明禁用原因，例如缺员工、无适用卡、租户冻结。

toast 只能作为补充，不得作为失败或成功的唯一反馈。

### 12.4 交互闭环补充

- `O-RESOURCE-DELETE`：资源删除必须先打开确认态，展示待删除资源和影响范围；有关联未来排期、服务项目占用，或删除后启用资源少于 1 个时，确认按钮禁用并展示阻断原因。
- `O-SCHEDULE-SUCCESS`：保存草稿或发布成功后必须刷新 `O-SCHEDULE-HOME` 对应日期，定位并高亮新时段；发布失败保留表单输入和预检结果。
- `M-BOOKING-DETAIL`：会员从我的预约进入详情，详情承接待服务、候补、已完成和已取消四类状态；只有符合规则的待服务预约可进入取消确认。
- `M-CANCEL-BLOCK`：超过取消截止或租户冻结时不进入确认取消，直接展示阻断原因、取消截止时间和门店联系方式，确认取消按钮不可用。
- `A-FREEZE`：后台冻结租户必须填写原因并二次确认，页面同时展示店长、教练、会员端影响；成功后刷新租户详情和操作记录。
- `A-CONFIG-EDIT`：配置修改使用独立编辑态或右侧抽屉，必须展示配置键、类型、单位、当前值、新值、影响范围和操作原因；成功后刷新配置列表当前行。
- `O-REPORT-DETAIL`：MVP 报表下钻只在报表明细页内完成，通过标签、筛选和列表切换维度，不新增独立会员、会员卡、服务或员工详情页。
- `O-FEEDBACK`：作为四端操作反馈研发说明，覆盖店长、教练、会员和平台后台的 loading、成功、失败、字段错误、页面阻断和禁用原因。

### 12.5 空态结构

核心空态必须包含：

1. 为什么为空。
2. 系统已经知道什么。
3. 推荐主操作。
4. 替代路径。
5. 完成后页面会发生什么变化。

必须覆盖：无员工、无服务、无会员、无会员卡、无排期、报表无数据、今日无服务、无可用卡、无预约记录、租户列表无结果和操作记录无结果。

`A-TENANTS` 为查询型数据表例外：租户列表无结果时仅在表格内容区显示“暂无数据”，不追加引导说明或“查看全部租户”按钮；总数为 0 时隐藏分页。其他业务流程型空态仍遵循上述五项结构。

### 12.6 可访问性

- 表单必须有可见 label，不得只用 placeholder。
- 字段错误必须能关联到对应字段。
- 后台按钮、筛选、分页、弹窗和表格行操作必须支持键盘访问。
- 键盘焦点态必须可见，不得移除 outline 后没有替代样式。
- 后台抽屉支持通过关闭按钮、点击非抽屉区域或按 Esc 关闭；抽屉和弹窗打开后，焦点进入弹层，关闭后返回触发元素。
- 动效必须支持减少动态效果降级。
