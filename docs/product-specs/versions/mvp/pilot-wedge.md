# 闲遇 MVP 试点楔子

版本：MVP  
文档日期：2026-06-07  
状态：active supplement  
文档性质：当前 MVP 的分阶段实现与试点优先级说明，不替代 `spec.md` 的完整产品范围

## 1. 结论

闲遇 MVP 保留完整多业态约课平台基线，但第一阶段产品、设计和工程应优先验证一个更窄的试点楔子：

> 面向康复理疗、儿童体适能、运动训练等预约制门店，优先验证“会员卡权益台账 + 员工核销 + 低余额 / 到期预警”是否能解决店长真实痛点。

本文件不删除完整 MVP 的服务项目、资源、员工、排期、预约、候补、取消、报表和冻结能力。它只声明第一阶段的交付顺序、UI 重排重点和工程映射优先级。

## 2. 为什么先做试点楔子

当前完整 MVP 覆盖店长端、员工端、会员端和平台后台四端闭环，适合作为产品基线。但首版如果一次性主推完整约课平台，容易让真实需求验证变得模糊：

- 用户不用时，难判断是没有需求，还是配置链路太长。
- 店长只需要卡余额和核销时，完整约课会变成过早建设。
- 会员仍习惯微信预约时，完整服务筛选、候补和取消规则可能低频。
- MVP 不做线上支付，必须靠线下实收、核销和预警证明经营价值。

试点楔子的核心验证问题是：

> 店长是否愿意把会员权益和核销事实交给闲遇管理？

如果这个问题成立，完整排期、会员自助约课、候补、报表下钻和平台续期都可以从权益事实账本自然扩展。

## 3. 首批目标用户

### 3.1 推荐试点门店

首批建议聚焦符合以下条件的门店：

- 康复理疗门店。
- 儿童体适能或运动训练门店。
- 有一对一服务或小班服务。
- 有预付费会员卡。
- 有 2 名以上履约员工。
- 会员卡剩余次数、有效期、员工核销或续卡提醒已经造成管理压力。

### 3.2 暂不优先

以下门店不作为第一阶段优先验证对象：

- 纯散客、无会员卡的门店。
- 只由店长一人履约、没有员工分工的门店。
- 已深度依赖成熟垂直系统的门店。
- 强依赖线上收款、退款、分账或发票的门店。
- 主要价值在营销裂变、优惠券、分销或积分的门店。

## 4. 第一阶段验证痛点

### 4.1 会员卡余额不可信

痛点成立的证据包括：

- 店长查剩余次数需要翻 Excel、微信群、纸卡或聊天记录。
- 员工核销后没有及时同步。
- 会员对剩余次数、有效期或扣次产生争议。
- 店长无法快速知道哪些卡快用完。

### 4.2 核销事实不可信

核销不是简单扣次数，而是门店履约事实。痛点成立的证据包括：

- 员工服务后忘记记录。
- 店长月底才发现漏扣或错扣。
- 到店、服务和扣卡之间没有清晰顺序。
- 店长不知道某次扣卡是谁操作的。

### 4.3 到期和低余额提醒不及时

预警是第一阶段的经营抓手。痛点成立的证据包括：

- 店长靠记忆提醒会员续卡。
- 已到期会员没有及时跟进。
- 会员卡剩 1 到 2 次时无人提醒。
- 续卡机会流失后才被发现。

### 4.4 线下收款后没有经营记录

MVP 不做线上支付，但门店仍需要知道线下卖了多少卡。痛点成立的证据包括：

- 售卡金额散落在聊天、收款截图或手工账里。
- 店长无法按月份查看售卡金额。
- 实收金额和会员卡权益没有绑定记录。

## 5. 第一阶段范围

### 5.1 必须优先交付

第一阶段优先级高于完整约课体验的能力：

- 店长创建会员。
- 店长创建会员卡模板。
- 店长给会员发卡并录入线下实收金额。
- 系统生成邀请码，会员绑定后查看卡包。
- 员工查看今日需要到店或核销的会员。
- 员工先到店确认，再核销。
- 核销后更新会员卡余额、会员记录和报表。
- 店长查看低余额、即将到期和已过期预警。
- 店长查看本月线下售卡、到店和核销摘要。
- 平台后台观察租户是否完成发卡、是否发生核销、是否触发预警、是否通过客服续期。

### 5.2 保留但弱化

以下能力属于完整 MVP 基线，应保留模型和后续入口，但第一阶段 UI 不作为主叙事：

- 完整服务项目管理。
- 资源管理。
- 排期发布。
- 会员自助筛选服务和预约。
- 候补。
- 复杂取消规则。
- 报表多维下钻。

弱化不是删除。后续进入第二阶段时，这些能力应能从第一阶段的数据模型继续扩展。

### 5.3 继续不包含

继续保持 MVP 剔除项：

- 微信授权手机号。
- 平台内线上支付、微信支付、退款、分账、发票。
- 会员自助购卡、在线充值、在线续费。
- 文件上传、图片上传、头像上传、二维码上传、附件上传。
- 员工自助注册。
- 优惠券、拼团、分销、积分商城。
- 员工薪酬结算和财务对账。

## 6. UI 重排方向

### 6.1 店长端

第一阶段店长端工作台应优先回答：

1. 今天要核销什么。
2. 哪些会员卡快用完或快到期。
3. 本月线下售卡和核销是否清楚。
4. 下一步还缺哪些配置。

后续设计审查应重点检查：

- 工作台是否能一眼看到待到店、待核销、低余额、即将到期和本月实收。
- 添加会员并发卡是否足够靠前。
- 报表首页是否优先展示售卡、到店、核销和会员卡提醒。
- 服务、资源、排期是否保留为后续完整约课入口，而不是压过核销台账主线。

### 6.2 员工端

第一阶段员工端主路径应是：

```text
今日服务 / 待核销名单 -> 到店确认 -> 核销确认 -> 记录完成
```

员工资料、服务记录和我的页可保留，但不应压过到店和核销。

### 6.3 会员端

第一阶段会员端主路径应是：

```text
邀请码绑定 -> 核对门店与会员卡 -> 卡包 -> 核销记录 / 预约记录
```

会员端第一阶段先建立权益可信感。完整服务筛选、服务详情、候补和取消流程可作为第二阶段体验升级。

### 6.4 平台后台

平台后台保留试用、冻结和人工续期边界，同时补充试点观测重点：

- 租户是否完成发卡。
- 是否发生员工核销。
- 是否产生低余额或到期预警。
- 冻结页是否展示。
- 店长是否查看或复制客服微信。
- 是否人工续期并解冻。

## 7. 工程映射优先级

当前 `docs/architecture/versions/mvp/` 已按三阶段完成工程映射，实现事实见 `implementation-status.md` 和 `prototype-implementation-map.json`。

### 7.1 Phase 1：权益事实账本

优先实体：

- `Member`
- `CardTemplate`
- `MemberInviteCode`
- `MemberCard`
- `OfflineSaleRecord`
- `AttendanceConfirm`
- `DeductionRecord`
- 直接基于事实表的实时报表与预警查询

关键要求：

- 发卡和线下实收必须绑定。
- 到店确认和核销必须可追溯操作人和时间。
- 核销记录必须能更新会员卡余额。
- 低余额、即将到期和已过期预警必须可查询。

### 7.2 Phase 2：完整预约

扩展实体和能力：

- `ServiceItem`
- `Resource`
- `StaffServiceBinding`
- `BookableSlot`
- `Booking`
- 会员自助约课
- 候补
- 取消规则

关键要求：

- Phase 1 的核销记录必须能关联 Phase 2 的预约记录。
- 如果第一阶段存在简化服务安排，第二阶段应能迁移到标准 `BookableSlot` 和 `Booking`。

### 7.3 Phase 3：经营系统

扩展能力：

- 报表下钻。
- 平台续期转化观测。
- 多业态入口扩展。
- 更复杂的门店运营指标。

## 8. 成功标准

第一阶段试点成立需要看到以下信号：

- 至少 3 家目标门店完成真实访谈。
- 至少 2 家门店承认会员卡余额、核销或到期提醒是每周都会遇到的问题。
- 至少 1 家门店愿意导入真实会员卡数据试用。
- 至少 1 家门店愿意让员工用系统完成真实核销。
- 试用期间产生真实 `OfflineSaleRecord`、`AttendanceConfirm` 和 `DeductionRecord`。
- 店长至少每周 3 次查看预警或核销记录。
- 试用结束时，至少 1 家门店愿意继续使用或明确接受人工续期。

如果这些标准达不到，应继续收窄问题，不应扩大到完整排期平台。

## 9. 真实世界作业

正式改版前应完成 3 家门店观察。每家只看四个动作：

1. 店长添加一个新会员并卖一张卡。
2. 店长查一个老会员的剩余次数和有效期。
3. 员工完成一次到店和核销。
4. 店长找出本周低余额或快到期会员。

每个动作记录：

- 现在用什么工具。
- 花几分钟。
- 谁会出错。
- 错一次的后果是什么。
- 店长是否愿意为这个问题付费。
- 如果只能上线一个功能，店长会选哪个。
