# 闲遇 MVP Acceptance Criteria

版本：MVP  
文档日期：2026-05-30

## 1. 文档与版本规范

- `docs/product-specs/versions/mvp/` 必须是完整独立版本包。
- MVP 版本包必须包含 `README.md`、`spec.md`、`requirements-list.md`、`acceptance-criteria.md`、`implementation-notes.md`、`prototype-notes.md`。
- `docs/design-docs/versions/mvp/prototype.html` 必须存在，并作为 MVP UI 设计稿依据。
- MVP 正式文档不得要求阅读任何其他版本资料。
- MVP 实现和验收只以当前 MVP 版本包与当前 UI 设计稿为依据。

## 2. 产品边界

- MVP 必须采用通用约课模型：服务项目、员工、资源、会员卡、预约时段、预约、到店确认、核销、报表。
- 服务项目名称和类型必须允许门店自定义，不得限定为瑜伽、健身、普拉提、舞蹈等单一行业。
- 店长和会员小程序不得调用微信授权手机号能力。
- 员工小程序不得提供微信登录和自助注册。
- 全部端不得出现线上支付、购买、订单支付、退款、发票、分账、支付二维码上传。
- 全部端不得出现任何文件上传入口，包括头像、图片、二维码、附件、资质。
- 会员端无可用卡时必须提示联系门店，不得出现购卡或支付入口。

## 3. 店长小程序

- 店长微信登录页品牌必须显示“闲遇-店长端”，不得在右侧重复展示“店长端”。
- 店长微信登录页作为固定首屏不得发生上下拖动；页面必须适配状态栏、微信胶囊、底部安全区和矮屏设备，且不得截断登录操作。
- 店长首次微信登录且无门店时，必须进入开始使用流程。
- 首次进入店长端开始使用流程前，必须展示新用户告示，说明新用户已获得免费使用权益和当前试用天数；当前默认试用天数为 30 天，由平台配置决定。
- 新用户告示必须提供 `我知道了` 确认按钮；确认后进入开始使用引导页，不提供关闭或跳过入口。
- 开始使用页必须说明门店资料、营业时间、履约资源为必填，员工、服务、会员卡、会员、排期可分步补充。
- 开始使用页必须展示三个必填项的完成状态；创建门店按钮默认禁用，只有门店资料、营业时间和至少 1 个启用资源均保存并校验通过后才可点击。
- 三个必填项完成后，开始使用页必须将三条清单切换为已完成状态并解锁创建门店按钮；不得在按钮前重复展示完整门店预览或额外的可创建确认卡。
- 首次开店流程采用清单式引导，店长从 O-START 点击必填项进入 O-STORE、O-HOURS 或 O-RESOURCE，保存成功后返回 O-START 更新完成状态。
- O-RESOURCE 通过完成按钮的可用状态表达是否满足开店资源要求，不额外展示“已满足开店资源要求”提示卡；资源、员工和服务列表的圆形新增按钮使用几何居中的加号。
- O-START 必须采用固定首屏且不可上下拖动，只展示门店资料、营业时间和履约资源三个可操作项，不展示员工、服务或会员等无法在本页操作的后续配置。
- 点击创建门店时必须进行服务端最终校验，成功后一次性创建门店和资源，并跳转 O-DASHBOARD 工作台。
- 门店资料必须包含门店名称、服务范围、城市、区/县、详细地址、联系电话、营业时间。
- 门店名称必须在全平台已创建门店中唯一；名称规范化后相同也视为重复。开店草稿不得抢占名称，最终创建或修改遇到并发重复时必须返回明确的门店名称已被使用错误。
- 城市与区/县选项必须来自后端数据库接口，前端不得内置完整行政区划映射；保存时后端必须校验区/县属于所选城市。
- 门店地址必须使用底部抽屉填写，字段顺序为城市、区/县、详细地址，三个字段均为必填并分别显示红色“必填”标记；不展示省/直辖市字段，抽屉内不额外展示合成地址；保存后由后端合成完整展示地址。
- 联系电话保持必填自由文本，不做格式校验或跨门店重复校验。
- 服务范围必须由店长自行填写 1 到 6 个短标签，不得依赖系统预置或推荐标签；保存时必须有成功或错误反馈。
- 门店资料页首次开店场景主操作必须明确为保存并返回清单，不得触发连续自动跳转。
- 门店资料页首次开店场景不得出现页面说明卡、营业时间补齐步骤、营业时间字段或完整门店展示预览。
- 营业时间必须支持按星期设置营业/休息和开始结束时间。
- O-START、O-STORE 和 O-HOURS 均不得重复展示完整门店预览；店长需要复核时通过对应清单项返回编辑，完成态只保留已完成摘要与创建门店主操作。
- 营业时间页首次开店场景主操作必须明确为保存并返回清单，不得触发连续自动跳转。
- 营业时间页首次开店场景不得出现完整门店资料预览，只能保留营业时间配置、可预约时间摘要和返回清单提示。
- 资源管理必须支持新增、修改、删除、停用、排序和容量设置。
- 资源管理列表态必须提供资源行修改和删除入口；启用/停用状态只能作为只读标识展示，不得伪装成单独操作按钮。
- 新增资源保存后必须回到资源管理列表态，列表态用于确认可预约资源并返回开店清单。
- 资源删除必须二次确认，确认态必须展示资源名称、类型、容量、启用状态和删除影响；有关联未来排期、服务项目占用，或删除后启用资源少于 1 个时，必须禁用确认并提示先处理阻断原因。
- 资源删除提交中必须禁用重复提交；删除成功后返回资源列表并刷新资源数量，删除失败时保留确认态并展示错误原因。
- 首次启用流程中资源管理完成后的主操作必须返回开店清单，不得进入创建员工账号。
- 资源管理列表态不得提供独立排序管理入口；排序通过新增或修改资源表单中的排序字段维护。
- 新增资源必须使用底部抽屉或等价移动端弹层，字段必须包含资源名称、资源类型、默认容量、排序和启用状态。
- 新增资源的资源类型必须支持固定快捷项和自定义，固定项为房间、场地、床位、设备、工位；咨询室、护理间等场景词应作为资源名称或自定义类型，不作为默认固定项。选择“自定义”后必须显示自定义类型必填输入框；保存时将去除首尾空格后的真实输入值写入 `resourceType`，不得提交“自定义”占位值；编辑已有非固定类型资源时必须自动选中自定义并回显原值。
- 新增资源默认容量最小为 1，启用状态默认启用；停用资源不得进入新排期资源选择。
- 门店保存时必须校验至少存在 1 个启用资源。
- 门店资料页不得展示开店进度或已填数量卡片；门店名称、门店地址、联系电话和服务范围必须用红色“必填”标记。
- 营业时间页不得展示开店必填、已营业、可预约三个统计卡片；营业日必须在周一至周日的统一选择区设置，所有已选日期进入同一份逐日时间列表，不得再展示独立周末设置。
- 创建员工账号必须从员工列表右上角新增员工进入底部抽屉完成，字段包含姓名、角色标签、登录账号、初始密码、确认密码；登录账号按 Unicode NFKC、去除首尾空白和小写转换后必须全平台唯一，同租户、跨租户、大小写或兼容字符等价的重复创建均返回 HTTP 409 和 `STAFF_LOGIN_NAME_TAKEN`，列表不得新增重复行；冲突时保留表单并在登录账号字段提示更换；初始密码和重置密码至少 8 位；创建成功或取消后回到员工列表；新增员工抽屉不得提供复制账号操作。
- 员工列表不得展示待完善状态统计；员工列表行必须一键复制员工姓名、登录账号和当前登录密码，打开修改抽屉必须自动读取并回显账号全部信息，不得要求店长为日常查看或复制先重置密码。员工列表只返回 `credentialAvailable`，不得批量返回密码；复制和编辑通过所属店长的单员工凭据接口按需读取，接口必须校验租户归属、限频、记录不含密码的审计，并返回 `no-store`。员工登录只校验 PBKDF2 哈希；可恢复凭据必须使用独立 AES-256-GCM 密文、随机 nonce、稳定租户与员工标识 AAD 和版本化密钥保存，数据库、幂等响应、审计和应用日志均不得出现明文密码。历史仅哈希账号必须返回凭据不可用并提供一次性设置新密码入口，设置后进入正常直接查看和复制流程。修改抽屉必须支持修改账号资料、密码、启用、停用和删除账号，且不得提供重复的独立复制卡片。修改为其他员工已占用的全局账号必须返回 `STAFF_LOGIN_NAME_TAKEN`，账号未变化时允许保存；停用账号继续占用名称，只有物理删除后才释放；两个并发创建相同规范化账号的请求最多一个成功。修改密码或停用账号必须撤销该员工已有会话，重新启用不得恢复旧会话。删除账号必须为物理删除，提交前必须校验是否存在关联服务项目、会员卡适用范围、未来排期等项目；有关联项目时必须禁用删除并提示用户先解除关联。
- 服务项目页默认展示“服务与排期”管理列表，列表行必须展示适用资源数、可履约员工数和服务时长；服务名称区保持中性并在容量说明下方以色点和文字展示可排期、草稿及缺失项、已停用状态，资源、员工和时长数据区分别使用绿色、暖黄色、灰色轻底色强化状态，不得显示胶囊状态标签或行内启停操作；页面支持全部、可排期、待处理筛选；新增和修改必须在当前列表页打开底部抽屉，表单按会员看到什么、每次如何预约、由谁和在哪里履约分组，不得展示服务状态卡、保存影响说明或启用前检查说明。
- 服务项目必须包含名称、类型、时长、默认容量、核销次数、适用资源、可履约员工；适用资源和可履约员工必须采用下拉多选，停用资源和停用员工不得被选中；选择超过 2 项时，选择框只展示“已选 N 个资源/员工”而不是完整名称列表。
- 服务项目名称按 Unicode NFKC、首尾空白清理、连续空白折叠和大小写归一化后必须在同一租户内唯一；不同租户允许使用同名项目，草稿和停用项目仍占用名称，修改时自身原名称不视为重复；同租户冲突返回 HTTP 409 和 `SERVICE_NAME_TAKEN`，保留表单并在名称字段提示；两个并发创建最多一个成功。
- 无员工时服务项目可保存草稿，但保存并启用和发布预约时段必须禁用，并提示先创建启用员工且绑定到服务。
- 修改服务抽屉必须在右上角更多菜单提供正常可点击的删除入口，不得因服务处于启用状态而预先禁用或常驻展示阻断文案；启用项目点击删除后必须提示先停用，不得进入删除确认或请求删除接口，服务端仍以 `SERVICE_MUST_BE_DISABLED` 兜底；草稿或停用项目点击后必须二次确认；仍关联会员卡适用范围或任意排期时必须返回 `SERVICE_IN_USE`，不得自动解绑或删除业务记录；无业务关联的草稿或停用项目物理删除后，资源和员工绑定一并清理，租户内服务名称可以再次使用。
- 会员卡管理页必须展示会员卡总数、次数卡数、期限卡数，支持全部、次数卡、期限卡筛选；不得展示“新建次数卡”和“新建期限卡”两个入口卡片，只保留一个新增按钮；新增按钮先选择卡类型，再进入现有新增会员卡页面，填写页不得再次展示次数卡/期限卡切换入口；点击已有会员卡进入修改页面，不得将新增页面改为抽屉。
- 会员卡只支持次数卡和期限卡，不得展示组合卡入口；次数卡必须包含卡名、售价、总次数、有效期、低余额提醒、适用服务、适用员工；期限卡必须包含卡名、售价、有效期、适用服务、适用员工，不得展示由平台后台统一配置的到期提醒；新增和修改页面不得展示“发给会员后怎么用”或“保存前检查”说明块。
- 会员卡的适用服务和适用员工必须采用下拉多选；选择超过 2 项时，选择框只展示“已选 N 个服务/员工”，不得完整铺开名称列表。
- 会员卡名称按 Unicode NFKC、首尾空白清理、连续空白折叠和大小写归一化后必须在同一租户内唯一；不同租户允许同名，启用和停用会员卡均占用名称，修改时自身原名称不视为重复；同租户冲突返回 HTTP 409 和 `CARD_TEMPLATE_NAME_TAKEN`，保留抽屉并在名称字段提示；两个并发创建最多一个成功。
- 会员卡售价必须支持 0 和两位小数，不能为负数；负数价格必须展示字段错误并禁用保存。
- 会员卡修改页必须常驻展示可点击的删除按钮；启用模板点击后必须提示先停用，服务端以 `CARD_TEMPLATE_MUST_BE_DISABLED` 兜底；停用且从未发卡的模板必须二次确认后物理删除，适用范围随模板清理并释放租户内名称；存在任意已发卡记录时必须返回 `CARD_TEMPLATE_IN_USE`，不得删除会员权益、售卡、预约、核销或审计历史，失败时必须展示明确原因。
- 添加会员必须填写会员姓名和联系方式，并支持生成邀请码、发放会员卡、录入门店线下实收金额；会员编号必须由后台生成且全平台唯一，请求不得接收或信任前端会员编号；添加页不得展示会员编号输入、“实收确认”提示卡或“保存后生成邀请码”提示卡；发卡成功后必须展示邀请码、有效期、绑定状态、复制/转交入口、过期重新生成入口和实收金额；不得向店长展示后台枚举值。
- 排期首页必须在当前日期列表上使用底部抽屉新增时段，点击草稿行在同一抽屉续编；不得再跳转独立发布页面。抽屉关闭后列表滚动位置和日期上下文不得被重置，页面与抽屉均不得显示滚动条。
- 排期必须支持选择服务、员工、资源、日期和开始时间；时段容量自动采用所选履约资源容量，结束时间由服务端依据服务时长生成，客户端不得提交容量或可信结束时间。服务选择后只展示已绑定的启用员工和资源，重叠占用项必须明确标记且不可选择。
- 排期提交发布时必须由服务端预检未来时间、营业时间、员工/资源绑定、员工/资源重叠和同时覆盖服务和员工的启用会员卡；失败时通过提交提示反馈原因，抽屉不展示完整检查清单，完整选择仍可保存草稿。发布请求必须在事务内再次预检，数据库必须阻断同租户已发布时段的员工或资源重叠并返回明确冲突。
- 排期保存草稿和发布成功后必须展示成功反馈，关闭抽屉、定位或保留 O-SCHEDULE-HOME 对应日期、刷新并高亮新保存或新发布的时段；刷新失败时必须提示手动刷新。
- 工作台“发布预约时段”任务不得以会员数量作为排期发布硬前置；配置缺失时跳转首个服务/员工/资源/会员卡范围缺口，已有未来草稿时进入对应日期并打开该草稿，配置完整且无草稿时进入排期页自动打开新增抽屉；已有未来已发布时段后不再展示“发布预约时段”首个预约待办。
- 工作台创建后待办态必须展示开放预约前配置进度和下一步待办，不展示无价值的 `今日预约 0 / 待到店 0 / 待核销 0` 指标。
- 工作台运营态必须展示今日预约总量、待履约和已完成；只有存在会员卡提醒或排期草稿时才显示“店长要跟进”，没有真实跟进事项时隐藏整个区域；员工端负责到店确认和权益处理，店长端不得重复提供到店或扣卡操作；店长任务聚焦查看履约进度、跟进低余额、处理临期会员和排期草稿，不得直接重复底部导航文案。
- 工作台不承载完整报表，趋势、明细和月份筛选必须进入 O-REPORT。
- 报表首页必须面向店长优先呈现销售额、预约、到店、核销四个结果，并支持本月、上月、选月份、全部范围；售卡明细、预约到店、服务表现、会员卡提醒应以店长可理解的入口呈现，低余额、即将到期和已过期需进入“今天先处理”。
- 报表明细的下钻范围必须收敛在 O-REPORT-DETAIL 内，通过标签、筛选和列表切换售卡、预约、到店、核销、服务表现、员工维度和会员卡提醒；MVP 不新增独立会员详情、会员卡详情、服务详情或员工详情页。
- 冻结后店长端必须强制进入 O-FROZEN 服务冻结页；除 O-FROZEN 外不得访问工作台、我的、员工、服务、会员卡、会员、排期、报表等页面，也不得通过深链进入任何业务或设置页面。

## 4. 员工小程序

- 员工必须通过店长创建的账号密码登录。
- 员工首次登录必须进入完善资料页。
- 员工资料只支持文字信息和系统占位标识，不得上传头像。
- 员工登录后必须能看到归属门店资料摘要，至少包含门店名称、地址、联系电话、营业时间和服务范围。
- 员工只能看到自己被排入的服务时段。
- 今日服务页必须展示服务名称、时间、资源、预约人数、待到店、待核销。
- 今日无服务时必须展示空态，提示检查个人资料或联系门店排期。
- 预约名单必须展示会员、会员卡、核销次数、预约状态和卡异常提醒。
- 核销前必须先到店确认。
- 到店确认成功页必须展示会员身份、会员卡状态和本次扣减规则，并提供继续核销入口。
- 核销确认必须展示扣前次数、核销次数、扣后次数。
- 会员卡过期、余额不足或未到店时必须禁止核销，并展示阻断原因。
- 服务记录必须支持员工建议和会员反馈文本。
- 教练端我的页必须展示账号状态、归属门店资料、资料编辑入口、重置密码联系门店和退出登录。
- 冻结后员工端不得查看完整名单、到店确认、核销或新增服务记录。

## 5. 会员小程序

- 会员必须通过微信一键登录，仅识别 openid。
- 未绑定会员身份时必须进入邀请码绑定流程。
- 邀请码绑定流程必须明确分为填写邀请码、加载门店信息、核对门店并确认绑定三步；会员点击查询门店信息时不得直接完成绑定。
- 加载门店信息时必须展示查询中状态，并说明正在校验邀请码有效期、绑定状态和可绑定会员卡。
- 邀请码有效时必须展示目标门店资料供会员核对，目标门店资料至少包含门店名称、地址、联系电话、营业时间和服务范围，同时展示会员姓名和可绑定会员卡权益，并在会员点击确认绑定后才绑定门店会员身份和会员卡权益。
- 核对门店并确认绑定页必须提供返回修改入口；会员发现门店、姓名或会员卡不一致时不得被强制绑定。
- 邀请码无效或过期时必须进入绑定失败页，并显示联系门店。
- 会员绑定后必须能在卡包或约课首页查看门店资料摘要，至少包含门店名称、地址、联系电话、营业时间和服务范围。
- 卡包必须展示卡名、剩余次数、有效期、适用服务和状态。
- 约课首页必须支持按日期、服务类型、员工和可约状态查看预约时段。
- 服务详情必须展示服务、员工、资源、时间、容量、取消规则和可用会员卡。
- 确认预约时只能展示适用该服务、未过期、余额足够的会员卡。
- 预约成功必须生成预约记录、占用名额，并同步到员工端预约名单。
- 满员时可以记录候补意向，但不得自动补位、不得占用名额、不得扣减会员卡。
- 我的预约必须展示待服务、已完成、已取消、候补，并支持查看详情和符合规则的取消。
- 预约详情必须展示预约状态、服务、员工、资源、时间、适用会员卡、取消规则、候补说明或完成核销摘要；已完成、已取消和候补状态必须有清晰只读说明。
- 取消预约页必须展示取消影响；取消成功后释放名额，不产生核销；超过取消规则或租户冻结时必须进入取消阻断态，说明阻断原因、取消截止时间和门店联系方式，确认取消按钮禁用且不得释放名额或变更预约状态。
- 服务完成后会员必须能查看核销记录、员工建议和会员反馈。
- 会员端我的页必须展示会员资料、绑定门店资料、卡包入口、预约入口和退出登录。
- 冻结后会员端不得约课、取消或候补，只能查看只读卡包摘要和联系门店。

## 6. 平台后台 WEB 端

- 后台必须提供独立登录页，登录页包含平台说明、账号、密码、登录按钮和必要错误提示。
- 后台不得提供注册入口。
- 后台登录状态失效且接口返回 `LOGIN_REQUIRED` 或 `UNAUTHORIZED` 时，前端必须清除本地会话并自动跳转登录页；账号密码错误、权限不足和租户冻结不得触发该跳转。
- 登录后必须进入可交付的后台管理系统页面，侧栏包含租户管理、客服微信、平台配置和操作记录；租户期限调整从租户列表行操作进入右侧抽屉。
- 后台所有右侧抽屉打开后，点击非抽屉区域或按 Esc 必须能够关闭抽屉。
- 侧栏会话区的角色固定显示“平台管理员”，账号必须显示当前认证用户的真实 `username`，不得使用静态示例账号。
- 租户列表必须展示由店长首次微信登录自动开通的租户，租户状态包括试用中、即将到期、已冻结、已延长，并支持搜索、状态筛选、到期筛选和分页；行操作必须以按钮组呈现，不得仅显示纯文字。
- 后台不得提供新建租户、新建试用租户或创建门店入口；MVP 的租户开通入口只在店长端首次微信登录流程。
- 租户详情必须展示租户状态、门店资料、业务摘要，以及冻结对店长端、教练端和会员端的影响。
- 后台冻结租户必须进入二次确认态，展示租户名称、当前到期日、冻结原因、三端影响和历史数据保留说明；原因缺失或未勾选确认时必须禁用确认冻结，提交中必须禁用重复操作，成功后返回租户详情并刷新状态。
- 系统必须定时冻结试用或延长期限已过期且尚未冻结的租户，写入冻结原因和系统来源操作记录；已冻结租户不得重复冻结。
- 后台必须仅在冻结状态展示延期并解冻入口，并能调整租户使用期限后解冻；新到期日早于当前日期或操作原因缺失时必须禁止保存。
- 后台必须能配置客服微信文本信息，未配置时展示默认客服微信。
- 后台必须能查看和修改平台运营配置，至少包含新租户默认试用天数、租户即将到期提醒天数、邀请码默认有效天数、预约默认取消截止分钟数和会员卡到期提醒天数；配置修改必须进入编辑态，展示配置项名称、配置键、类型、单位、当前值、新值、影响范围、操作原因和生效说明；配置修改必须校验值类型和范围，操作原因缺失时必须禁止保存，保存成功后刷新配置列表当前行。
- 平台配置修改不得批量改写已有租户到期日、已生成邀请码或已发布预约时段，只影响之后的新业务流程。
- 操作记录必须记录自动试用开通、冻结、延期并解冻、客服微信和平台配置变更，包含触发来源或操作人、时间、旧值、新值和原因。
- 后台不得提供会员支付、门店售卡收款、退款、文件上传、二维码上传或图片上传。

## 7. UI 与可用性

- 原型必须覆盖店长、教练、会员和平台后台关键页面，教练端和会员端必须分开设计，不得混合在同一组业务画板中。
- 原型必须覆盖开发链路地图、通用服务项目、资源管理列表态、资源管理新增资源底部抽屉态、员工账号、会员卡售价、报表、冻结解冻。
- 原型必须覆盖教练端今日无服务、到店确认成功、核销阻断和我的页；会员端候补成功、取消预约和我的页；后台租户详情、平台配置和操作记录。
- 表单字段必须有 label。
- 关键按钮触控区域不小于 44px。
- 移动端并排按钮间距不小于 8px。
- 保存、发布、确认预约、取消预约、确认到店、确认核销、冻结、延期并解冻和平台配置修改类操作必须有 loading、成功或错误反馈；店长端保存、发布、发卡和创建账号也必须展示统一反馈规范。
- 四端统一反馈必须覆盖字段错误、表单错误、页面级阻断、禁用原因、重复提交禁用和成功后刷新来源页/列表/结果态；toast 只能作为补充，不得作为唯一反馈。
- 状态必须用文字和颜色共同表达。
- 店长、教练和会员小程序采用松绿色、深墨色、珊瑚橙、数据蓝、提示金和 8px 业务卡片。
- 平台后台采用“企业经纬”视觉：深海军蓝侧栏、冷灰白工作区、商务蓝主操作、紧凑表格和 3-5px 容器圆角，不使用渐变装饰或营销页式大标题。

## 8. 报表验收

- 创建会员卡时录入售价，给会员发卡时可带出并修改实际售价。
- 发卡保存后必须生成线下售卡记录。
- 本月销售额必须按售卡日期筛选并汇总已录入销售额。
- 销售额、预约、到店和核销必须支持按本月、上月、选月份和全部范围查看。
- 点击销售额必须进入售卡明细，展示会员、卡名、实收金额和售卡日期。
- 点击核销必须进入核销明细；核销成功后必须更新会员卡余额，并进入核销统计。
- 余额低于阈值、14 天内到期、已过期必须以店长可理解的提醒文案展示，并能从对应提醒进入会员或会员卡跟进。
