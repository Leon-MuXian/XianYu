# Prototype Checklist

文档日期：2026-05-30

## 文件检查

- `../design-docs/versions/mvp/prototype.html` 必须存在。
- HTML 必须能被标准 HTML parser 解析。
- 页面标题应能识别产品名和当前版本。

## 覆盖检查

- UI 设计稿必须覆盖 active 版本包定义的关键页面。
- 页面 ID 应与 active 版本包的 spec 和 requirements-list 对齐。
- 每个画板标题必须包含页面 ID、端、页面名；状态画板必须在标题中标明状态。
- 页内抽屉或弹层状态必须保留底层页面语义，避免被误读为独立详情页。
- 关键业务链路必须覆盖服务项目、资源、员工、会员卡、排期、预约、到店、核销、报表和冻结。
- 资源删除必须覆盖二次确认和阻断态；排期发布必须覆盖成功反馈和回到排期首页后的刷新/高亮。
- 会员预约必须覆盖预约详情和取消阻断态；后台必须覆盖冻结租户二次确认和平台配置编辑态。
- O-FEEDBACK 必须作为四端操作反馈研发说明，不能只约束店长端表单。

## 视觉与可用性检查

- 关键状态必须同时使用文字和颜色表达。
- 表单字段必须有 label。
- 关键按钮触控区域不小于 44px。
- 移动端画板不应出现内容横向溢出。
- 桌面后台画板可以保持固定宽度，但应在设计说明中明确。
- UI 原型或设计说明必须声明设计 token，包括颜色、字体、字号、间距、圆角和组件状态。
- 组件必须能追溯到 `docs/DESIGN.md` 中的按钮、标签、表单、列表、抽屉、空态和表格规则。
- 小程序端必须说明 320px、375px、390px、430px 的响应式处理策略，并明确不同微信小程序机型、安全区、字体缩放和底部导航的自适应方案。
- 平台后台必须说明 1024px、1280px、1440px、1920px 和宽表格的处理策略，并明确不同桌面和笔记本屏幕大小下的侧栏、筛选区、表格和行操作自适应方案。
- 页面必须考虑长门店名、长地址、长服务名、长员工名、长会员卡名和 10 个服务标签的展示。
- 表单反馈必须覆盖 loading、成功、字段错误、表单错误、部分成功和禁用态。
- 核心空态必须包含“为什么为空、系统已经知道什么、下一步主操作、替代路径、完成后变化”，不得只写“暂无数据”。
- 报表明细下钻必须明确收敛在 O-REPORT-DETAIL 内，不得在 MVP 原型中暗示独立会员、会员卡、服务或员工详情页。
- 后台和 Web 端交互必须有键盘焦点态说明。
- 表单错误必须说明如何关联到字段，不得只依赖 toast。
- 动效必须说明减少动态效果时的降级方式。

## 首屏优先级检查

- O-START 首屏主任务必须是完成三项必填并创建门店。
- O-DASHBOARD 创建后待办态首屏主任务必须是推进开放预约前下一步。
- O-DASHBOARD 运营态首屏主任务必须是今天先处理什么。
- O-REPORT 首屏必须优先展示销售额、预约、到店和核销四个结果。
- O-SCHEDULE-HOME 首屏必须优先展示日期和待发布/异常时段。
- O-MEMBER-HOME 首屏必须优先展示添加会员、待绑定或会员卡预警。
- 平台后台租户列表首屏必须优先支持搜索、筛选和状态处理。
- 每个核心页面首屏最多呈现 1 个主任务和 3 个次任务，其余内容进入下方区域或详情。

## 边界检查

- MVP UI 不应出现当前版本未定义的业务入口。
- 无可用会员卡时不得出现线上购卡或支付入口。
- 文件上传、线上支付和手机号授权不属于当前 MVP 范围。
